# 失败模式与对策

规则没生效、被抱怨、或产生副作用时，先在这里对号。

| 失败模式 | 症状 | 对策 |
|---|---|---|
| 过度触发 | 规则在琐碎场景反复发作，用户开始嫌烦 | 加作用域上限（模式 6）；琐碎豁免 |
| 模糊规则 | 同一规则每次执行结果不一样 | 改写为可核查的具体形式（模式 2） |
| 规则膨胀 | 简单意图被写成九行三段 | 砍到三行最小结构；重要性不靠篇幅表达 |
| 触发不足 | 该发作时没发作 | 触发条件写入字面短语；检查是否被更长、更泛的其他规则稀释 |
| 层级冲突 | 规则与用户当轮指令打架，模型僵硬执行规则 | 加优先级对齐条款（模式 5） |
| 来源未把关 | 规则引用的"惯例"其实出自低质来源 | 引用前验证权威性（官方文档/源码优先），见 `sources.md` |
| 隐性不合规 | 明文规则被执行，但推理过程中夹带抵触态度（如把合理约束描述为负担） | 态度是执行的一部分：规则的精神与字面同属合规范围；发现即修正表述，而非只在字面上照做 |
| 全大写依赖 | 规则靠 MUST/NEVER 堆强度，实际照样被违反 | 删大写，改写理由（模式 1）；强度来自具体性和边界，不来自音量 |

## 两个元教训

1. **"没拦住我" ≠ "允许我"**。工具或框架对某条路径不设防，不代表它
   是被支持的用法；规则写作同理——不要因为某行为未被禁止就当作默认
   接受。
2. **验证深度要匹配故障的惰性**。有些故障在启动/冒烟测试期完全不显现
   （惰性故障），"看起来正常"不是证据。为规则设计的验证也要覆盖到
   核心链路，而不只是入口。
